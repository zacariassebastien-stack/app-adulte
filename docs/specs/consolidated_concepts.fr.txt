============================================================
3. PHILOSOPHIE DU PIMENT
============================================================

Le piment n'est PAS une note de préférence personnelle.

Les PA, valeurs personnelles, exclusions, enchères, etc. gèrent la volonté personnelle du joueur.

Le piment sert principalement de GATE DE PROGRESSION :
"À quel point serait-il prématuré que cette possibilité apparaisse au début de la partie ?"

Référence :

Piment 1 :
- introduction
- peut apparaître dès le début sans escalade brutale

Piment 2 :
- érotisation
- clairement intime/sexuel ou psychologiquement engageant
- mais pas encore une pratique sexuelle explicite majeure

Piment 3 :
- sexualité explicite / engagement marqué
- ne doit pas apparaître immédiatement

Piment 4 :
- très engageant
- réservé à une partie fortement escaladée
- peut être physique OU psychologique

IMPORTANT :
Le numéro d'un stade d'évolution ne détermine PAS automatiquement son piment.
Exemple :
- Masturbation = 3/3/3
- Pénétration vaginale = 4/4/4

4. MODIFICATEURS DE ZONES
============================================================

Pour les cartes GÉNÉRIQUES dont la zone est un paramètre :

piment_effectif = min(4, piment_intrinsèque + modificateur_zone)

Modificateurs validés :

+0 :
- visage / cheveux
- cou / nuque
- bras / mains
- dos / épaules
- ventre
- jambes hors cuisses
- pieds

+1 :
- cuisses
- fesses
- poitrine / seins

+2 :
- pénis / vulve
- anus

IMPORTANT :
- "entrejambe par-dessus vêtements" n'est PAS une zone.
- l'état vestimentaire est distinct de la zone.
- ne pas ajouter le modificateur à une pratique qui contient déjà intrinsèquement la zone.
  Exemple : Doigter vaginal ne reçoit pas encore +2.
- idem pour pénétration vaginale, footjob, etc.

Pour une variante "zone libre" :
- le joueur ne peut choisir qu'une zone dont le piment effectif respecte le plafond global courant.
- la zone libre ne doit jamais permettre de contourner la progression.

============================================================
5. NOUVEAU MODÈLE : UNE CARTE CONCEPTUELLE = UNE UNITÉ DU DECK
============================================================

L'ancien modèle "une variante/stade = une occurrence séparée dans le deck" doit être remplacé.

Une carte conceptuelle avec plusieurs évolutions apparaît UNE SEULE FOIS comme concept dans le deck/stock logique.

Exemple :
Photo mutuelle 1/2/4 = un concept, pas trois cartes.

Au moment de sélectionner/jouer le concept :
- proposer les stades actuellement autorisés par le piment global ;
- le joueur choisit le stade qu'il souhaite réellement utiliser.

Exemple Photo mutuelle 1/2/4 :
global 1 -> stade 1
global 2 -> stades 1 et 2
global 3 -> stades 1 et 2
global 4 -> stades 1, 2 et 4

Le joueur n'est JAMAIS obligé de choisir le stade le plus élevé disponible.

Si le piment global augmente pendant qu'un concept reste en main :
- les nouveaux stades autorisés deviennent immédiatement disponibles.
- pas besoin de repiocher une autre occurrence.

Les variantes peuvent rester dans le catalogue comme définitions d'actions.
Elles cessent d'être des unités de deck.

============================================================
6. QUOTA D'UTILISATION PAR CONCEPT
============================================================

L'ancien système générique :
première utilisation -> DISCARD -> seconde utilisation -> CONSUMED
doit être remplacé.

Nouveau principe :

Un concept possédant N stades d'évolution possède N utilisations maximales par cycle.

Exemple :
- concept à 1 stade -> normalement 1 utilisation/cycle
- concept à 3 stades -> 3 utilisations/cycle

IMPORTANT :
le joueur peut choisir LE MÊME STADE plusieurs fois.

Exemple :
Masturbation 3/3/3 :
3 utilisations disponibles.
Il est possible de choisir le premier stade trois fois si ce sont les choix effectués.

On consomme donc :
- une utilisation du CONCEPT
et NON
- "le stade utilisé".

Toute utilisation réellement engagée doit compter dans le même quota conceptuel, y compris lorsqu'elle vient d'un mécanisme secondaire qui utilise réellement la carte.

Ne pas conserver parallèlement l'ancienne règle générique de seconde utilisation via DISCARD si elle devient redondante avec ce quota.

============================================================
7. CAS SPÉCIAL 006 / 007
============================================================

006 et 007 ne deviennent PAS des cartes à évolutions.

Elles doivent rester deux concepts différents :
- retirer 1 vêtement
- retirer 2 vêtements

La présence aléatoire de l'une ou l'autre dans la pioche fait partie du gameplay.

En revanche, leur ancienne multiplicité physique dans le deck doit disparaître.

Représentation souhaitée :
- un concept 006 + compteur/capacité d'utilisation
- un concept 007 + compteur/capacité d'utilisation

La capacité reste dérivée des vêtements initiaux selon les règles existantes validées.

Ancienne référence :
occ006 = min(2, T)
occ007 = ceil((T - occ006) / 2)
où T = nombre initial de vêtements.

Conserver le comportement fonctionnel voulu, mais ne plus matérialiser plusieurs copies du concept dans le deck.

============================================================
8. IDENTITÉ IMMUTABLE DE CHAQUE UTILISATION
============================================================

Point critique réseau/persistance :

Le concept peut être réutilisé avec :
- un autre stade
- une autre zone
- une autre direction
- d'autres paramètres
- une autre valeur personnelle
etc.

Il ne faut donc PAS réutiliser naïvement le même ancien occurrenceId pour plusieurs usages différents.

Chaque utilisation engagée doit créer une identité/snapshot IMMUTABLE contenant au minimum les données nécessaires à la reconstruction exacte de cette utilisation :
- concept
- variante/stade choisi
- directions/cibles
- paramètres résolus
- accessoires si concernés
- valeur personnelle/éléments nécessaires aux calculs historiques
- toute donnée nécessaire au reconnect/retry/apprentissage/résolution

L'identité d'usage doit rester stable pendant tout le cycle de vie de cette utilisation :
réservation -> engagement -> enchère -> compromis/corruption éventuels -> résolution -> apprentissage -> historique.

Les retries et reconnexions doivent retrouver la même utilisation, pas en fabriquer une nouvelle.

Le schéma exact doit être choisi après inspection des dépendances actuelles.
Si une décision architecturale importante non décrite ici est nécessaire, demander validation avant de l'imposer.

============================================================
9. NOUVELLE LOGIQUE DE PIOCHE
============================================================

OBJECTIF :
le nombre de variantes ou d'évolutions d'un concept ne doit plus augmenter mécaniquement sa probabilité de pioche.

Une carte conceptuelle = une seule candidate de pioche.

Le piment global :
- fixe ce qui est AUTORISÉ.

Soft / Épicé / Intenable :
- fixe ce qui est FAVORISÉ parmi les possibilités autorisées.

Anciennes pondérations à conserver pour l'instant, mais à appliquer correctement AUX CLASSES DE CONCEPTS et non aux occurrences :

SOFT :
- piment 1 : 45 %
- piment 2 : 40 %
- piment 3 : 13 %
- piment 4 : 2 %

ÉPICÉ :
- piment 1 : 20 %
- piment 2 : 40 %
- piment 3 : 30 %
- piment 4 : 10 %

INTENABLE :
- piment 1 : 10 %
- piment 2 : 25 %
- piment 3 : 40 %
- piment 4 : 25 %

Si certaines classes sont impossibles à cause du plafond global :
- redistribuer proportionnellement leur poids entre les classes actuellement autorisées.

Exemple Épicé avec global 3 :
poids originaux 20/40/30/10
classe 4 interdite
=> normalisation des 20/40/30 :
environ 22,2 / 44,4 / 33,3 / 0.

Processus conceptuel :
1. déterminer les concepts candidats ;
2. déterminer leur classe de pioche courante ;
3. choisir une classe selon les poids du style normalisés ;
4. choisir uniformément un CONCEPT admissible de cette classe ;
5. mettre ce concept en main.

Ne PAS choisir une occurrence/stade avant le concept.

============================================================
10. CLASSE DE PIOCHE DYNAMIQUE
============================================================

Pour une action simple :
classe de pioche = son piment.

Pour une carte à évolutions :
classe de pioche = piment maximal du stade ACTUELLEMENT ACCESSIBLE.

Exemple Entrave 1/2/3 :
global 1 -> classe 1
global 2 -> classe 2
global 3 ou 4 -> classe 3

Exemple Photo mutuelle 1/2/4 :
global 1 -> classe 1
global 2 -> classe 2
global 3 -> classe 2
global 4 -> classe 4

Cela ne signifie PAS que le joueur devra utiliser le stade correspondant à la classe de pioche.
Il pourra sélectionner n'importe quel stade actuellement autorisé.

============================================================
11. CAS PARTICULIER DES ZONES LIBRES POUR LA PIOCHE
============================================================

Les concepts génériques à zone libre ne doivent pas tous remonter artificiellement dans les classes hautes simplement parce qu'une zone très intime est possible.

Règle validée :

classe_pioche_zone_libre =
max(1, piment_maximal_actuellement_accessible - 1)

Le -1 concerne UNIQUEMENT LA CLASSE DE PIOCHE.

Il ne modifie jamais le piment réel de l'action choisie.

Exemple Jeu de main, base 1 :
global 1 :
- max accessible 1
- classe pioche 1

global 2 :
- max accessible 2
- classe pioche 1

global 3 :
- max accessible 3
- classe pioche 2

global 4 :
- max possible toujours 3
- classe pioche 2

Une fois la carte jouée :
- bras -> piment réel 1
- cuisses -> piment réel 2
- pénis/vulve -> piment réel 3

Le plafond global reste impératif.

13. NETTOYAGE ATTENDU
============================================================

Le but n'est PAS d'empiler le nouveau moteur au-dessus de l'ancien.

Après identification précise des dépendances, supprimer ce qui devient réellement obsolète :

- matérialisation d'un stade/variant comme carte indépendante dans le deck

- ancien modèle générique première utilisation + DISCARD + deuxième utilisation, lorsqu'il est remplacé par le quota conceptuel

- catalogue mort
- cartes supprimées
- variantes/stades devenus redondants ou incohérents
- branches de compatibilité internes inutiles

Conserver uniquement les structures encore nécessaires aux fonctionnalités validées.

En revanche :
- ne jamais modifier les migrations Supabase déjà déployées

- reconnect
- idempotence
- historique

- compromis
- corruption
- Recovery

etc.
